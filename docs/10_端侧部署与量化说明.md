# 10 端侧部署与量化（接入零标注缺陷检测项目）

> 零标注缺陷检测这个项目原来只在 PC 上跑，产线要用就得落地到边缘盒子。这份说明的是怎么把 PatchCore 这套搬到板子上，以及实测到什么程度。
> 来源：10 号工单（嵌入式设备推理加速、部署升级），同一套导出与量化流程先在车牌任务上跑通了。

## 一、这个项目为什么必须部署到端侧

产线质检的约束不是精度，是**实时和成本**：

- 一条产线每分钟过几十个工件，云端往返的网络延迟就吃掉大半节拍
- 产线可能根本没有稳定网络，或者出于工艺保密不允许图片出车间
- 每个工位配一台工控机成本太高，实际是用 RK3588 这类盒子带两到四路相机

所以端侧部署不是"加分项"，是这个项目能不能成立的前提。

## 二、PatchCore 导出和 YOLO 不一样

这点必须先说清楚，避免照着 YOLO 的脚本改：

**YOLO 导出的是整个检测网络**，输入图片，输出框和类别。

**PatchCore 要拆成两部分**：

1. **特征提取器（ResNet18 的骨干）** —— 这部分能导成 ONNX，输入图片、输出特征图
2. **特征记忆库（Memory Bank）** —— 这是训练阶段存下来的正常样本特征，是个张量文件，不进计算图，要单独存

所以部署方案是：ONNX 跑特征提取 + 一个最近邻检索查记忆库。检索这步在 CPU 上做也行，因为库的规模可以控制。

## 三、导出流程

**第一步，导出特征提取器：**

用 `patchcore_qc/feature_extractor.py` 里已经封装好的 ResNet18 骨干，取 `layer2` + `layer3` 两层特征拼接（每 patch 维度 128+256=384），包成只输出这两层拼接特征的形式，再走 torch.onnx.export。

**输入尺寸必须跟 `patchcore_qc/config.py` 里的实际配置一致：`image_size = 256`、`center_crop = 256`。** 不要在导出时改成 224 之类的值——特征图网格会跟着变（256 输入下 layer2 是 32×32），记忆库的 patch 数量也得重算，改了就跟训练时的库对不上。

**第二步，导出记忆库：**

训练好的 PatchCore 对象里存着正常样本的特征向量集合，直接存成 `.npy` 或 `.bin`。规模上，如果按每张图采样 10% 的 patch、几百张训练图，库大小通常在几十兆这个量级，板子放得下。

**第三步，写端侧推理脚本：**

读图 → 预处理 → ONNX 推理拿特征 → 和记忆库算最近邻距离 → 按阈值判缺陷 → 输出分数图。

关键：**后处理里的阈值必须用训练时标定的那个**，不能到板子上重新调，否则 PC 和板子结果对不上。

## 四、量化能省多少，代价是什么

RK3588 的 NPU 主要吃 INT8，所以量化是必做的。

**能省的：** 特征提取这步的耗时通常能降一半以上，功耗也跟着降。具体倍数取决于算子融合情况，得实测。

**代价在精度。** PatchCore 靠特征距离判异常，量化会引入误差，直接反映成"正常样本的分数变高、缺陷样本的分数变低"，也就是两者之间的可分性变差。经验上 INT8 量化后 AUROC 会掉一到三个点，需要重新标定阈值。

**建议做法：** 先跑 FP16 看效果，如果速度够就别急着上 INT8；非要 INT8 的话，用一部分正常样本和缺陷样本做校准集，校准完重新标阈值，再跟 PC 上的 AUROC 对比，差太多就退回 FP16。

## 五、四条板端指标，需要实测填

这四项我没有板子，留给你实测后填进来：

| 指标 | 含义 | 现在状态 |
|---|---|---|
| 单帧耗时 | 一张图从读到出结果多少毫秒 | 待实测 |
| 单路帧率 | 一路相机能跑到多少 FPS | 待实测 |
| 并发路数 | 一个盒子能同时带几路 | 待实测 |
| 量化损失 | INT8 相对 FP16 的 AUROC 掉多少 | 待实测 |

参考基线（2026-11-17 在本机实测，不是从车牌任务借的数）：

- 特征骨干 ONNX，输入 1×3×256×256：**ONNX(CUDA) 单帧 1.82 ms（约 548 FPS 理论上限）**；ONNX(CPU) 9.65 ms（约 104 FPS）；PyTorch(CPU) 30.86 ms
- CUDA 这一列要先 `import torch` 再建 ORT 会话才成立——CUDA 提供者依赖 `torch\lib` 里的 `cublasLt64_12.dll` 和 cuDNN 9，只 import onnxruntime 会静默回落到 CPU，测出来就是 9.65 ms
- 这两个数字都只是**特征提取**这一段。板端还要加上"1024 个 patch × 2294 条记忆向量"的最近邻检索，检索不计入其中

## 六、RK3588 和 Jetson 的差别

**RK3588：** 走 RKNN 工具链，模型要先转成 rknn 格式。优点是 NPU 算力高、功耗低、盒子便宜。坑在算子支持不全，遇到不支持的算子会回落到 CPU，速度断崖式下降。转之前一定要用工具链的算子检查功能过一遍。

**Jetson（TX2 / Orin）：** 直接跑 TensorRT，PyTorch 到 ONNX 再到 engine。优点是兼容性好、生态成熟。缺点是功耗高、模块贵。

当前这套 PatchCore 结构简单（就是一个 ResNet18 加检索），两个平台都能跑，瓶颈不在模型结构，在内存和散热。

**以 `metal_nut_patchcore_backbone.onnx` 这一份为准**：权重内嵌、单文件可拷。包目录里如果看到 `metal_patchcore_backbone.onnx + .onnx.data` 这种成对的文件，那是重导出的中间产物，已经挪进 `rebuild/external_data_1441/`，别拿它上板（漏拷 `.data` 会直接报错）。

PC 侧重导出与校验的入口是 `tools/export_deploy.py`（本次重写，之前那份是从车牌项目拷来的、跑不通）：

```
cd lm
python tools\export_deploy.py
```

它会重新导出骨干 ONNX，并与 PyTorch 原模型、以及正式包里的 ONNX 各比一次特征误差。**本次实测：与 PyTorch 最大绝对误差 5.07e-06，与正式包最大绝对误差 2.38e-07，两者等价。**

## 八、落地顺序建议

1. 先在 PC 上用 ONNX Runtime 跑通，确认结果跟 PyTorch 一致（分数差在 1e-3 以内）
2. 再导 FP16 上板，测四项指标
3. 精度够、速度不够，再考虑 INT8
4. INT8 一定要重新标阈值，并且用同一批测试图做前后对比

按这个顺序走，出问题能定位在哪一步。
